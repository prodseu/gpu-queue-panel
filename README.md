# GPU Queue Panel

一个轻量的个人GPU任务队列面板。Windows本机打开网页，通过SSH查看Linux服务器；服务器不开放网页端口。后端仅用Python标准库，前端无需构建。

功能：自动识别GPU、点击显卡查看该卡个人队列、总队列、显存/计算利用率、服务器持续缓存的5分钟曲线、取消单个等待项、拖拽排序、空队列持续待命。所有示例中的服务器信息均为`XXX`，真实配置和运行数据不进入Git。

## 一行加入托管队列

```bash
qrun --gpu 2 -- python train.py --epochs 20
CUDA_VISIBLE_DEVICES=2 qrun python train.py --epochs 20
```

服务器安装一次qrun入口后即可使用，不必改训练代码。也支持接入后的`python train.py --queue --queue-gpu 2 ...`。详情见[CLI_USAGE.md](CLI_USAGE.md)，方案比较见[SUBMISSION_RESEARCH.md](SUBMISSION_RESEARCH.md)。

## 快速使用

环境：两端Python 3.10+和SSH；服务器安装tmux、NVIDIA驱动/nvidia-smi。Windows端可直接双击启动脚本。

1. 把源码放到本机及服务器。两端都复制`config.example.json`为`config.json`，替换`XXX`：

   ```json
   {
     "ssh_host": "XXX",
     "remote_dir": "/XXX/gpu-queue-panel",
     "remote_python": "/XXX/bin/python"
   }
   ```

   以上是要修改的主要字段；其余字段保留模板值。`ssh_host`填写自己已配置免密登录的SSH别名，`remote_dir`填写服务器源码目录。`config.json`已被Git忽略。

2. 在服务器复制`examples/queue.example.json`为`queue.local.json`，填写每项已授权任务的工作目录、命令参数、GPU UUID、进度字段和实际总更新数，再导入：

   ```bash
   python3 cli.py init queue.local.json
   ```

   导入不会执行命令，也不会接管已有进程。不要把正在运行的训练重复导入。任务ID保持稳定；参数使用JSON数组，命令保持前台运行，不再套tmux/nohup。CPU任务设`gpu: null`、`gpu_uuid: ""`。可选`completion_file`存在时要求其JSON包含`complete: true`。

3. 在服务器启动专用tmux：

   ```bash
   bash start-server.sh                 # 仅监控，不启动任务
   bash start-server.sh --execute       # 明确执行刚导入的任务
   ```

   两种模式二选一；已有同名会话时脚本不会再启动或切换模式。也可直接运行`python3 server_agent.py run --execute`。执行器按最新清单顺序领取，最多同时执行窗口数量的任务；GPU有未纳管计算进程时等待。不会结束他人任务或自动重跑失败任务。训练程序应遵循`CUDA_VISIBLE_DEVICES`，使用逻辑GPU编号。

4. 本机双击`Start-Queue.cmd`。也可在终端运行：

   ```powershell
   python launch.py
   python cli.py console
   ```

   图形界面仅监听本机`127.0.0.1`。服务器持续采样并保存5分钟曲线，关掉本机仍记录，重新打开直接加载。首次部署先积累5分钟真实数据；断档留空。绿线为GPU-Util，蓝线为显存占用比例，均为0—100%；GPU-Util不是逐SM硬件occupancy。

启动后根据服务器快照自动显示实际显卡数量。点击任意显卡卡片，查看自己在该卡运行和等待的任务；点击“总队列”查看全部当前任务，包括CPU任务。卡片显示运行/等待数量，选择在刷新后保留，按GPU UUID关联任务。

同时显示该卡的GPU计算进程及PID、Python、显存。已纳管运行任务关联自己的启动身份；其余进程标记“不可操作”，没有拖拽、取消、终止入口，也不加入执行清单。外部进程的名称/Python取自NVIDIA提供的进程名，不读取其命令行、目录、环境、日志或Python安装文件。共用Unix账号不代表已获授权；只有身份记录匹配的已登记进程可读取自身命令行。CPU程序仅展示已登记任务，不遍历全服务器进程。

忽略本人留卡进程时，`hold_rules`需包含明确的`identity`（`pid`、`start_ticks`、`boot`）及原script/GPU条件；缺少身份记录的未知进程保持只读且会阻塞占用GPU的领取，不会为识别它而读取命令行。任务旧启动记录若只有PID，也保持保守显示，不擅自猜测归属。

按卡查看时，上下移动或拖拽只交换该卡任务占据的等待位置，其他卡和CPU任务的位置保持；“总序”是其全局等待序号。总队列中可以统一调整所有等待项的顺序。以上是同一份队列的不同视图，执行受全局并发窗口和资源保护约束。

执行模式没有领取截止时间，队列跑空后持续待命。之后已授权任务经同一QueueStore锁事务加入即可接续，无需重启；不自动新增训练、重跑失败项或增加训练轮数。

## Codex / 命令行

先查看实际ID和顺序，修改后再查看确认：

```powershell
python cli.py status
python cli.py cancel task-b
python cli.py reorder task-c task-a
```

服务器对应命令为`python3 cli.py status/cancel/reorder`。排序必须给出全部剩余等待ID。取消B只移除B，不影响A/C；运行中的项不能在这里终止或重排。文件锁和原子写入保证图形界面、Codex和执行器使用同一队列。

## 范围与验证

这是**单服务器有界并发队列**，不同任务可指定不同GPU，同卡并跑受显存和利用率启动保护；不自动迁移GPU或跨服务器调度。未知/占用GPU不会被自动抢占；默认失败后停止后续执行，等待项保留，`stop_on_failure: false`可改为继续独立任务。重启发现旧运行项时不会自动重跑，需要先人工检查。

```bash
python -m unittest discover -v
node --check web/app.js
```

可选界面检查需安装Playwright及Chromium，运行`python qa_gpu_views.py`。检查使用隔离清单和本机临时端口，验证按卡/总队列、重排保留其他卡位置、取消、GPU数量与编号变化，不访问真实SSH或GPU。

`runtime-data/`、`client-data/`、本机配置、令牌和日志都应留在各自机器上。自定义数据目录时也应加入`.gitignore`。训练脚本、模型、数据、实验专用收尾代码及运行截图不随源码发布。


## 并发窗口与资源保护

默认队列窗口为 **2（全局同时执行上限，CPU任务也计入）**，网页可设1–8，并可修改显存余量、显存占用上限、单任务预计峰值、计算利用率阈值和启动间隔。修改通过revision和队列锁保存；缩窗只停止补位，已有运行项自然完成。任务仍按等待顺序启动，不跳过被资源保护拦住的队首。

默认保留8 GiB空闲显存，占用上限90%，单任务峰值预算24 GiB；计算利用率默认`-1`（不限制），同卡启动间隔默认60秒。显式启用计算阈值时，默认连续30秒低于阈值才考虑启动。显存允许量取`min(总显存−预留量, 总显存×占用上限)`；预计用量包括当前实际占用、运行项尚未分配的峰值预算和新任务预算。领取时固定该任务的峰值预算，之后降低网页默认预算不会减少运行项的预留。预算包含训练、验证峰值，可在任务登记时用`peak_memory_mib`（MiB）覆盖默认值。无历史的新任务应保守提高预算；本工具不做CUDA容量探测。

NVIDIA信息缺失、未知进程占卡、显存不足或计算利用率高时，只暂停领取。窗口为2表示最多2项，资源不够时可能只跑1项。运行项独立收尾，取消/重排只作用于等待项。失败不自动重试，停止后续领取的原规则保留；已经运行的其他任务继续完成。当前工具仅在全部任务结束的空闲边界执行共享汇总，单任务完成检查和CPU审计仍在各自执行路径内。

这些设置是**启动保护，不是显存或算力硬配额**。任务的后续显存突增、预算低估及其他程序后来占用仍可能导致OOM；训练本身也可能达到100% GPU利用率。工具不会强杀、暂停训练、自动改batch或修改模型来压利用率。新窗口不能承诺程序永不卡死。

### -1：逐项取消限制

所有网页调度参数支持整数`-1`，逐项判断，不参与普通阈值运算：

| 参数 | -1 的含义 |
| --- | --- |
| 并发窗口 | 不设并发数量上限；其他资源门仍独立生效 |
| 保留空闲显存 | 不设固定空闲余量；占用百分比门仍生效 |
| 显存占用上限 | 不设百分比上限；固定余量门仍生效 |
| 默认任务峰值 | 不额外预留默认峰值预算；任务显式登记预算仍优先，运行项已固定预算保持 |
| 计算利用率阈值 | 不因计算利用率高低、缺失或缺少低利用率历史而阻塞启动（默认） |
| 连续低于阈值时间 | 启用计算阈值时仅检查当次利用率，不等待历史 |
| 同卡启动间隔 | 不设启动冷却时间 |

MiB/GiB转换保留`-1`原值。两个显存限制均为`-1`时不再检查显存限额；未知进程只读边界和队列身份检查始终保留。`0`、其他负数和超范围值不表示关闭，仍拒绝保存。
